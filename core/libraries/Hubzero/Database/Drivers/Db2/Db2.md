# DB2 Driver

> **This is a proof-of-concept driver. While the SQL output is syntactically correct, fundamental issues with DB2's catalog cache design prevent many tests from passing reliably during rapid DDL changes (CREATE/DROP TABLE cycles). This driver is not maintained on a regular testing cadence and should not be considered production-ready without re-validation.**

> **This driver requires a patched `pdo_ibm` extension.** The stock PECL `PDO_IBM` has a critical bug where column descriptors are cached in memory and never refreshed when a prepared statement is re-executed. This causes SQL0204N ("object not found") and SQL0601N ("name already exists") errors after schema changes. The extension was patched to free stale column descriptors on re-execution. See the [Technical Notes](#technical-notes-pdo_ibm-catalog-cache-fix) section for details.

## Architecture

```
Drivers/Db2/
  Db2Driver.php   extends BaseSqlDriver
  Db2Syntax.php   extends BaseSqlSyntax
  Db2Grammar.php  extends BaseSchemaGrammar
```

`BaseSqlDriver` extends `BasePdoDriver` (PDO connection wrapper), which extends `Driver` (abstract connection lifecycle, query execution, result fetching). All 12 concrete drivers follow this same three-file pattern.

DB2 is the most heavily overridden of all the drivers. The driver must uppercase all identifiers, emulate autocommit for DML statements, strip microseconds from all fetched timestamps, work around multiple PDO_IBM bugs, and handle DB2's lack of several common SQL features (ENUM, UNSIGNED, IF NOT EXISTS, inline indexes, ON UPDATE CASCADE, column positioning). The grammar extends `BaseSchemaGrammar` (not a MySQL-specific grammar) since DB2's DDL syntax diverges significantly from MySQL.

| Property | DB2 | Base (MySQL) Default |

DB2 uses double-quote identifier wrapping and stores all unquoted identifiers as UPPERCASE. The driver uppercases all identifiers before wrapping.

### Auto-Increment via IDENTITY

```sql
"ID" INTEGER GENERATED BY DEFAULT AS IDENTITY (START WITH 1 INCREMENT BY 1)
```

DB2 uses `GENERATED BY DEFAULT AS IDENTITY` which allows explicit values (useful for testing and data migration). `GENERATED ALWAYS` would reject explicit inserts. The `PRIMARY KEY` constraint is added inline with the column definition. Identity columns are reset via `ALTER TABLE ... ALTER COLUMN ... RESTART WITH n`.

## Connection

The constructor builds a PDO DSN:

```
ibm:DATABASE={database};HOSTNAME={host};PORT={port};PROTOCOL=TCPIP;VALIDATE=RUN
```

Default port is 50000. `VALIDATE=RUN` defers table validation to runtime instead of bind/prepare time, which is needed for DDL operations in transactions where tables may not exist yet at prepare time.

ODBC fallback DSN:
```
odbc:DRIVER={IBM DB2 ODBC DRIVER};DATABASE={database};HOSTNAME={host};PORT={port};PROTOCOL=TCPIP;VALIDATE=RUN
```

For cataloged databases (local connections), the DSN is simply `ibm:{database}`.

Post-connection configuration:

- **`ATTR_CASE = CASE_LOWER`** — DB2 returns UPPERCASE column names by default; this normalizes them for ORM compatibility
- **`ATTR_STRINGIFY_FETCHES = true`** — PDO_IBM returns CLOB/BLOB columns as PHP resources (streams); this converts them to strings automatically

Uses the `pdo_ibm` PHP extension (patched build) or `pdo_odbc` fallback.

## Identifier Quoting

DB2 uses double-quote identifier wrapping (`"COLUMN_NAME"`). All identifiers are uppercased before wrapping since DB2 stores unquoted identifiers in uppercase. The `quoteName()` and `wrap()` methods handle this transparently:

```php
$this->quoteName('users')    // → "USERS"
$this->wrap('schema.table')  // → "SCHEMA"."TABLE"
```

Aliases are detected and handled: `table AS alias` becomes `"TABLE" AS "ALIAS"`.

## Query Building (Db2Syntax)

### Pagination

DB2 9.7+ uses SQL:2008 standard OFFSET/FETCH syntax (via the base class):

```sql
SELECT * FROM "USERS" OFFSET 10 ROWS FETCH FIRST 20 ROWS ONLY
```

### INSERT / Upsert

DB2 uses `MERGE` for upsert operations. Single-row upsert:

```sql
MERGE INTO "USERS" t
USING (SELECT ? AS "ID", ? AS "NAME" FROM SYSIBM.SYSDUMMY1) s
ON (t."ID" = s."ID")
WHEN MATCHED THEN UPDATE SET t."NAME" = s."NAME"
WHEN NOT MATCHED THEN INSERT ("ID", "NAME") VALUES (s."ID", s."NAME")
```

`SYSIBM.SYSDUMMY1` is DB2's equivalent of Oracle's `DUAL` table — a one-row system table for SELECT without a real table.

Bulk upsert uses `VALUES` as the MERGE source:

```sql
MERGE INTO "USERS" t
USING (VALUES (?, ?), (?, ?)) AS s("ID", "NAME")
ON (t."ID" = s."ID")
WHEN MATCHED THEN UPDATE SET t."NAME" = s."NAME"
WHEN NOT MATCHED THEN INSERT ("ID", "NAME") VALUES (s."ID", s."NAME")
```

### INSERT IGNORE

DB2 has no `INSERT IGNORE` syntax. For `INSERT IGNORE ... SELECT`, the driver uses `MERGE INTO ... WHEN NOT MATCHED THEN INSERT`. For simple inserts, the IGNORE flag is silently dropped (fallback to standard INSERT).

### Bulk INSERT

Standard multi-row VALUES syntax:

```sql
INSERT INTO "USERS" ("NAME", "EMAIL")
VALUES (?, ?), (?, ?), (?, ?)
```

### JSON Support (DB2 11.1+)

DB2 stores JSON as CLOB. JSON functions are supported on DB2 11.1+:

| Operation | DB2 SQL |
|-----------|---------|
| Path extraction | `JSON_VALUE(col, '$.path')` |
| Containment | `JSON_EXISTS(col, '$.path')` |
| Array length | `JSON_TABLE(col, '$[*]' COLUMNS ...)` with COUNT |

JSON paths use standard `$.key.subkey` syntax. Dot-notation paths are converted: `user.name` becomes `$.user.name`, `items.0.price` becomes `$.items[0].price`.

### Date Filtering

```php
// DATE("CREATED") = DATE(?)
$query->setDateWhere('created', '=', '2024-01-15', 'date');

// YEAR("CREATED") = ?
$query->setDateWhere('created', '=', 2024, 'year');
```

Supports `date`, `time`, `year`, `month`, `day` parts using native DB2 functions.

### Function Translation

| MySQL Function | DB2 Equivalent |
|---------------|----------------|
| `CONCAT(a, b, c)` | `(a \|\| b \|\| c)` |
| `IFNULL(a, b)` | `COALESCE(a, b)` |
| `NOW()` | `CURRENT TIMESTAMP` |
| `CURDATE()` | `CURRENT DATE` |
| `CURTIME()` | `CURRENT TIME` |
| `DATE_FORMAT(col, fmt)` | `VARCHAR_FORMAT(col, fmt)` |
| `SUBSTRING(col, s, l)` | `SUBSTR(col, s, l)` |
| `SUBSTRING_INDEX(str, d, n)` | `CASE/LOCATE/SUBSTR` combo |
| `UNIX_TIMESTAMP(col)` | `(DAYS(col) - DAYS('1970-01-01')) * 86400 + MIDNIGHT_SECONDS(col)` |
| `REGEXP col pattern` | `REGEXP_LIKE(col, pattern)` (DB2 11.1+) |
| `DATE_ADD(col, n DAYS)` | `(col + n DAYS)` |
| `DATE_SUB(col, n DAYS)` | `(col - n DAYS)` |
| `CONCAT_WS(sep, a, b)` | `(a \|\| sep \|\| b)` |

Date format codes are translated: `%Y` becomes `YYYY`, `%m` becomes `MM`, `%d` becomes `DD`, `%H` becomes `HH24`, etc.

### EXISTS Clause

DB2 requires every SELECT to have a FROM clause. The syntax class adds `FROM SYSIBM.SYSDUMMY1` to bare SELECT statements in EXISTS subqueries.

### TRUNCATE

DB2 requires the `IMMEDIATE` keyword and TRUNCATE must be the first statement in a unit of work:

```sql
TRUNCATE TABLE "USERS" IMMEDIATE
```

The driver issues a raw `COMMIT` before TRUNCATE to clear any pending implicit transaction.

## DDL Generation (Db2Grammar)

### CREATE TABLE

DB2 does not support inline indexes, IF NOT EXISTS, or MySQL table options:

```sql
CREATE TABLE "USERS" (
  "ID" INTEGER GENERATED BY DEFAULT AS IDENTITY (START WITH 1 INCREMENT BY 1) NOT NULL,
  "EMAIL" VARCHAR(255) NOT NULL,
  "NAME" VARCHAR(100),
  PRIMARY KEY ("ID")
)
```

Indexes are emitted as separate statements after CREATE TABLE:

```sql
CREATE UNIQUE INDEX "IDX_USERS_EMAIL" ON "USERS" ("EMAIL")
CREATE INDEX "IDX_USERS_NAME" ON "USERS" ("NAME")
```

Fulltext indexes are downgraded to regular indexes (DB2 Text Search requires separate administrative configuration).

### ALTER TABLE

DB2 ALTER TABLE syntax differs significantly from MySQL:

- **ADD COLUMN** — `ALTER TABLE "T" ADD COLUMN "COL" TYPE`
- **DROP COLUMN** — `ALTER TABLE "T" DROP COLUMN "COL"`
- **MODIFY type** — `ALTER TABLE "T" ALTER COLUMN "COL" SET DATA TYPE TYPE`
- **SET NOT NULL** — `ALTER TABLE "T" ALTER COLUMN "COL" SET NOT NULL`
- **DROP NOT NULL** — `ALTER TABLE "T" ALTER COLUMN "COL" DROP NOT NULL`
- **SET DEFAULT** — `ALTER TABLE "T" ALTER COLUMN "COL" SET DEFAULT value`
- **DROP DEFAULT** — `ALTER TABLE "T" ALTER COLUMN "COL" DROP DEFAULT`
- **RENAME COLUMN** — `ALTER TABLE "T" RENAME COLUMN "OLD" TO "NEW"`
- **Column positioning** — not supported (FIRST, AFTER, BEFORE all ignored)

Modify operations require separate statements for type, nullability, and default. The grammar splits a single column modification into up to three ALTER statements.

### Foreign Keys

DB2 does not support `ON UPDATE CASCADE`. The grammar converts it to `ON UPDATE NO ACTION`. `ON DELETE CASCADE`, `SET NULL`, and `RESTRICT` are supported.

### Computed Columns

DB2 supports generated columns via `GENERATED ALWAYS AS (expression)`. The `addStoredColumn()` and `addVirtualColumn()` methods both use stored (materialized) generated columns, as DB2 does not distinguish virtual and stored in the same way MySQL does.

### Zero-Date Handling

MySQL zero-dates (`0000-00-00 00:00:00`) are converted to `DEFAULT NULL` in column definitions, since DB2 does not accept zero-date values.

## Schema Introspection

DB2 uses the `SYSCAT.*` system catalog views for introspection:

| Method | Implementation |
|--------|---------------|
| `getTableColumns($table)` | `SYSCAT.COLUMNS` (colname, typename, length, scale, nulls, default) |
| `getTableKeys($table)` | `SYSCAT.INDEXES` + `SYSCAT.INDEXCOLUSE` |
| `getIndexes($table)` | `SYSCAT.INDEXES` + `SYSCAT.INDEXCOLUSE` |
| `getForeignKeys($table)` | `SYSCAT.REFERENCES` + `SYSCAT.KEYCOLUSE` |
| `getPrimaryKey($table)` | `SYSCAT.KEYCOLUSE` + `SYSCAT.TABCONST` (type = 'P') |
| `getTableList()` | `SYSCAT.TABLES` (type = 'T', current schema) |
| `getTableCreate($tables)` | Reconstructed from metadata (no `SHOW CREATE TABLE`) |
| `tableExists($table)` | `SYSCAT.TABLES` via `getTableList()` |
| `getAutoIncrement($table)` | `SYSCAT.COLUMNS` (identity = 'Y') + MAX query |
| `getCollation()` | `SYSIBM.COLLATIONS` |
| `getCharacterSet($table)` | `SYSCAT.DATATYPES` (CODEPAGE for VARCHAR) |
| `getEngine($table)` | Returns `'DB2'` (single storage engine) |
| `getVersion()` | `SYSPROC.ENV_GET_INST_INFO()` (service_level) |
| `getCheckConstraints($table)` | `SYSCAT.CHECKS` |
| `getSequences()` | `SYSCAT.SEQUENCES` |

### Uppercase Normalization

All table and column names are uppercased before querying SYSCAT views. Results are lowercased for ORM compatibility. LOB values returned as PHP resources are converted to strings via `stream_get_contents()`.

### Foreign Key Rule Codes

DB2 stores referential action rules as single characters. The driver translates them: `A` = NO ACTION, `C` = CASCADE, `N` = SET NULL, `R` = RESTRICT.

### No SHOW Commands

DB2 has no `SHOW TABLES`, `SHOW COLUMNS`, or `SHOW CREATE TABLE` equivalents. All introspection uses SYSCAT system catalog queries.

### ENUM (Not Supported)

DB2 has no ENUM type. `getEnumValues()` always returns an empty array. `addEnumValue()` and `removeEnumValue()` are no-ops.

### Views

- `createOrReplaceView()` — `CREATE OR REPLACE VIEW` (native support)
- `dropView()` — `DROP VIEW` with existence check via `SYSCAT.VIEWS`
- `viewExists()` — `SYSCAT.VIEWS` (current schema)
- `getViews()` — `SYSCAT.VIEWS` list

### Sequences (Native)

DB2 has native sequence support:

- `createSequence()` — `CREATE SEQUENCE` with START, INCREMENT, MIN/MAX, CYCLE, CACHE options
- `dropSequence()` — `DROP SEQUENCE` with existence check
- `sequenceExists()` — `SYSCAT.SEQUENCES` count
- `nextSequenceValue()` — `NEXT VALUE FOR "SEQ" FROM SYSIBM.SYSDUMMY1`
- `currentSequenceValue()` — `PREVIOUS VALUE FOR "SEQ" FROM SYSIBM.SYSDUMMY1`
- `getSequences()` — `SYSCAT.SEQUENCES` list

### Feature Detection

| Method | Returns |
|--------|---------|
| `getEngine()` | `'DB2'` |
| `supportsSequences()` | true (native) |
| `supportsUnsigned()` | false |
| `supportsExplicitNull()` | false |
| `supportsIfNotExists()` | false |
| `supportsJson()` | true (DB2 11.1+) |
| `supportsWindowFunctions()` | true |
| `supportsCTE()` | true |
| `supportsGeneratedColumns()` | true |

## Transaction Support

DB2 does not use `START TRANSACTION` or `BEGIN`. The driver toggles `ATTR_AUTOCOMMIT` and uses explicit `COMMIT`/`ROLLBACK` SQL:

```
transactionStart():
  depth 0 → setAttribute(ATTR_AUTOCOMMIT, 0)
  depth N → SAVEPOINT SP_N ON ROLLBACK RETAIN CURSORS

transactionCommit():
  depth 0 → SQL COMMIT + setAttribute(ATTR_AUTOCOMMIT, 1)
  depth N → RELEASE SAVEPOINT SP_N

transactionRollback():
  depth 0 → SQL ROLLBACK + setAttribute(ATTR_AUTOCOMMIT, 1)
  depth N → ROLLBACK TO SAVEPOINT SP_N
```

DB2 savepoints require the `ON ROLLBACK RETAIN CURSORS` clause to prevent cursor invalidation when rolling back to a savepoint.

### DML Autocommit Emulation

The `exec()` and `execute()` methods detect whether a statement is DDL (CREATE, DROP, ALTER, TRUNCATE, RENAME) or DML (INSERT, UPDATE, DELETE, SELECT). DML statements are wrapped in an implicit `beginTransaction()`/`commit()` pair. DDL statements are left unwrapped so PDO_IBM's native auto-commit handles them. This emulates MySQL's autocommit behavior on a database that doesn't auto-commit DML by default.

### Table Locking

`lockTable()` uses `LOCK TABLE ... IN EXCLUSIVE MODE`. `unlockTables()` is a no-op — DB2 releases locks automatically at transaction commit/rollback.

## Workarounds

### PDO_IBM PARAM_NULL Bug

`bindValue()` with `PDO::PARAM_NULL` causes "Unknown parameter type" error. The `bind()` method uses `PDO::PARAM_STR` for null values instead, which correctly inserts NULL.

### Newlines in Prepared Statements

PDO_IBM treats newlines as statement separators. The `prepare()` method replaces all `\r\n`, `\r`, and `\n` with spaces before preparing.

### TIMESTAMP Microsecond Stripping

DB2 TIMESTAMP columns return values with microsecond precision (e.g., `2024-06-15 10:30:00.000000`). All fetch methods (`loadObject()`, `loadObjectList()`) post-process results through `normalizeTimestamp()` to strip the microsecond suffix.

### No UNSIGNED Modifier

`normalizeColumnType()` strips `UNSIGNED` from all type definitions. MySQL-specific display widths are also removed: `INT(11)` becomes `INTEGER`, `BIGINT(20)` becomes `BIGINT`, `TINYINT(n)` becomes `SMALLINT`.

### No IF NOT EXISTS

DB2 does not support `CREATE TABLE IF NOT EXISTS`. `dropTable()` catches `SQL0204N` and `42704` errors to emulate `DROP TABLE IF EXISTS`.

### No Column Positioning

`addColumnAfter()`, `addColumnBefore()`, `addColumnFirst()`, `modifyColumnAfter()`, `modifyColumnBefore()`, and `modifyColumnFirst()` all silently ignore the positioning parameter and add/modify the column without position control.

### No FOREIGN_KEY_CHECKS

`disableConstraints()` and `enableConstraints()` are no-ops. Tables with foreign keys cannot be truncated without dropping constraints first.

### TRUNCATE Requires Clean Transaction State

`TRUNCATE TABLE` fails with `SQL0428N` if there is a pending transaction. The driver issues a raw `COMMIT` before every TRUNCATE to ensure a clean unit of work. After TRUNCATE, the identity column is reset via `ALTER TABLE ... ALTER COLUMN ... RESTART WITH n`.

### LOB Columns as Resources

PDO_IBM returns CLOB/BLOB column values as PHP stream resources. `ATTR_STRINGIFY_FETCHES = true` is set on connect to auto-convert. Default values from `SYSCAT.COLUMNS` may also be resources and are explicitly converted via `stream_get_contents()`.

### SET Type Conversion

MySQL `SET(...)` types are converted to `VARCHAR(255)` since DB2 has no SET type.

### Database Switching

DB2 doesn't support switching databases on an active connection. `select()` uses `SET SCHEMA` to change the current schema instead.

## Technical Notes: PDO_IBM Catalog Cache Fix

There are **two independent issues** that cause test instability with DB2, each operating at a different layer:

### Issue 1: PDO_IBM Stale Column Descriptors (Extension Bug — Patched)

The stock PECL `PDO_IBM` extension caches column descriptors in memory and **never refreshes them** when a prepared statement is re-executed. When tables are dropped and recreated between statement executions, the cached descriptors reference stale metadata.

**Root Cause:** In `ibm_statement.c`, function `ibm_stmt_executer()`, when re-executing a statement (`stmt->executed == 1`), the code calls `SQLFreeStmt(SQL_CLOSE)` to close the cursor but does not free the column descriptors stored in `stmt_res->columns`. These stale descriptors persist from the first execution.

**Fix Applied:**
```c
if (stmt->executed) {
    rc = SQLFreeStmt(stmt_res->hstmt, SQL_CLOSE);
    /* CATALOG CACHE FIX: Free stale column descriptors on re-execution */
    if (stmt_res->columns != NULL) {
        stmt_free_column_descriptors(stmt);
    }
}
```

This forces column descriptors to be reallocated on each execution, ensuring fresh metadata. The patch was built on PHP 8.3, Linux x86_64, against the DB2 CLI driver.

**Symptoms before patch:**
- SQL0204N ("object not found") on tables that exist
- SQL0601N ("name already exists") on tables that were dropped
- Stale metadata causing type mismatches
- ~50% test pass rate

**Result after patch:**
- Column metadata refreshed on every execution
- ~95% test pass rate

### Issue 2: DB2 Server Catalog Cache Bug (Engine Limitation — Unpatched)

DB2 12.1 has a server-level catalog cache bug that causes intermittent failures during rapid CREATE/DROP TABLE cycles **on the same table name when the table has a PRIMARY KEY constraint**. This was verified with the native DB2 CLP (no PHP/PDO involvement) on an empty database:

- Tables **without** a primary key: 100% reliable at any cycle count
- Tables **with** a primary key: catalog corruption after ~5-15 cycles

The failure mode is a "ghost table" state where:
1. `DROP TABLE` reports SQL0204N ("undefined name")
2. Yet `SYSCAT.TABLES` still shows the table as existing
3. The subsequent `CREATE TABLE` fails with SQL0601N ("name already exists")
4. Once triggered, the state cascades until the server internally recovers

No combination of `COMMIT`, `FLUSH PACKAGE CACHE DYNAMIC`, reconnection, `SET SCHEMA`, `ALTER TABLE DROP PRIMARY KEY`, or deferred-prepare settings reliably prevents or clears this state. It is a DB2 engine limitation.

**Practical impact:** This bug only manifests during rapid repeated CREATE/DROP of the same table name with a primary key — a pattern seen in test suites (setUp/tearDown), not in production use. The driver's SQL output is syntactically correct; the instability is in DB2's internal catalog management.

### Additional PDO_IBM Quirks

These issues exist in both stock and patched PDO_IBM and are handled by driver-level workarounds:

- **PARAM_NULL bug** — `bindValue()` with `PDO::PARAM_NULL` causes "Unknown parameter type"; use `PARAM_STR` for nulls
- **Newline handling** — PDO_IBM treats newlines as statement separators; driver strips them
- **LOB streams** — CLOB/BLOB values returned as PHP resources instead of strings; driver sets `ATTR_STRINGIFY_FETCHES`
- **Constructor driver_options** — some options may not take effect via the PDO constructor; driver uses `setAttribute()` after connecting

### Test Results

With the patched PDO_IBM extension:

- 21 test classes, 456 tests
- 17/21 classes pass 100% reliably
- 3-4 classes have intermittent failures due to DB2's catalog cache bug (not the PDO extension)
- Overall reliability: ~95%+ (up from ~50% before the patch)

The remaining intermittent failures are exclusively caused by the DB2 engine's catalog cache corruption during rapid DDL cycles with primary keys.
