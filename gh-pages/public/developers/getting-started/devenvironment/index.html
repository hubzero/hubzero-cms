    Developers

    Development environment

    The CMS does not run standalone. You develop against a working hub — a web server, PHP, a database, and a configured app/ directory — with this repository checked out in place of its CMS. This page separates what the repository gives you from what you have to get elsewhere.

    What this repository provides

    Everything here is in the tree and you can read it:

    Path What it does
    core/bin/muse The console. muse install bootstraps a hub from a checkout; muse migration applies schema changes. See the Muse reference.
    core/bin/composer A bundled Composer. Run it as php core/bin/composer install from core/.
    core/composer.json The PHP dependencies. The platform is pinned to PHP 8.2.30; the dev requirements are PHPUnit 11, PHP_CodeSniffer 3.13, PHPStan 2, parallel-lint, and Mockery.
    core/bin/php_tests.sh Runs phpcs --standard=PSR12 and parallel-lint over the files you name.
    docs/_tools/lint/ missing-facade-imports.php and undefined-language-keys.php.
    docs/_tools/docs/ and gh-pages/ The documentation builder and the reference generators.
    compose.yaml and .docker/ A development hub in Docker: this checkout served by FrankenPHP's PHP 8.2, with MariaDB and a mail catcher. See Developing in Docker.
    .github/workflows/ The CI. See below.

    What this repository does not provide

    Apart from the Docker setup for development, there is no Vagrantfile, no provisioning script, and no make-style setup target anywhere in the tree. Nothing here installs Apache, PHP, or MySQL on a machine; for a server, see the System administrators book.

    The .travis.yml at the root is left over from Travis CI. It declares PHP 8.2 and 8.3 and calls core/bin/php_tests.sh on the changed files. Nothing runs it now.

    Requirements

    muse install runs a pre-flight check before it does anything, and that check is the authoritative statement of what the CMS needs. From Install/Preflight.php:

    • PHP 8.2.0 or later.
    • These extensions: pdo, pdo_mysql, json, mbstring, openssl, curl, gd, fileinfo, zip.

    pdo_mysql is the only database driver required, and the installer connects with a mysql: DSN, so in practice the database is MySQL or MariaDB. The PHP lint workflow runs on 8.3, and Composer's platform is pinned to 8.2.30, so 8.2 and 8.3 are the versions the project actually exercises.

    Run php core/bin/muse install check on a candidate machine to see the pre-flight result without installing anything.

    Getting a hub to develop against

    Four routes:

    Docker Compose. docker compose up -d in a checkout starts a hub serving that checkout, with its database and a mail catcher beside it. It is the quickest way to a hub you can change; see Developing in Docker.

    Install one. The installation overview takes a Linux server from nothing to a running hub from a checkout of this repository, behind Apache, nginx or FrankenPHP in Docker, using the web installer or muse install. A development hub is the same, on a machine of your own.

    Autohub. A script that provisions a hub in a virtual machine using VirtualBox and Vagrant, with Workspaces and optionally Solr. It lives in a separate repository, hubzero/autohub, not here; nothing in this tree calls it or knows about it, and its own README is the only current description of it.

    muse install on your own LAMP stack. If you already have PHP 8.2+, a web server, and MySQL or MariaDB, the console can take a checkout of this repository the rest of the way. From the checkout root:

    php core/bin/composer install --working-dir=core
php core/bin/muse install

    muse install runs interactively and can also be driven a step at a time:

    Task What it does
    muse install check Pre-flight checks only, no changes
    muse install vendor Composer dependencies only
    muse install appdir Create the app/ directory structure
    muse install database Configure the database connection
    muse install settings Write the site settings and configuration files
    muse install schema Load the schema and essential data
    muse install migrations Run migrations to bring the schema up to date
    muse install sample Load sample data
    muse install admin Create the first administrator account

    This gets you the CMS. It does not get you the parts of a hub that are not the CMS: the tool session middleware, Workspaces, the mail gateway, LDAP, or Solr. For those you need the packages or Autohub.

    Note: The old version of this page pointed at a VMware image on hubzero.org/download. Nothing in this repository builds or references such an image; check whether it still exists before relying on it.

    Developing in Docker

    You need Docker with its Compose plugin. On Debian and Ubuntu that is sudo apt install docker.io docker-compose-v2. Then, from a fresh clone:

    git clone --branch 2.4-main https://github.com/hubzero/hubzero-cms.git
cd hubzero-cms
docker compose up -d
docker compose logs -f hub

    Put sudo in front of each docker command if your account is not in the docker group.

    The first start takes a few minutes. It builds the image, installs the Composer libraries into core/vendor/, installs the hub into app/ with the sample data, and starts the web server. When the log shows Installation Complete! and FrankenPHP's own lines follow it, press Ctrl+C to stop watching:
    The hub https://localhost:8443
    Its administrator interface https://localhost:8443/administrator, as admin with the password hubzero-admin
    The mail it sends http://localhost:8025, Mailpit's inbox
    Its database docker compose exec db mariadb -u hub -phub hub

    The certificate is one FrankenPHP makes itself, so the browser warns about it once. Both ports answer only on 127.0.0.1, and every password is in compose.yaml for anyone to read: this is a hub for your own machine, not for serving. For a real hub in Docker, see A self-contained hub in Docker.

    What runs

    Service What it is
    hub FrankenPHP's PHP 8.2 image with the hub's extensions, Xdebug and Composer's tools, built from .docker/Dockerfile. It holds no code: the checkout is mounted over /var/www/hub, so a change you save is the next request's code. .docker/hub-dev starts it.
    db mariadb:10.11, with the database in a Docker volume. It waits to be healthy before the hub starts, and creates the usage statistics' hub_metrics database on its first start.
    mail Mailpit. PHP's mail() in the hub's container hands every message to it, so nothing the hub sends leaves your machine.

    Each start runs muse install --env. The first time, that installs the hub from the HUB_* settings in compose.yaml. Every time after, it only runs the migrations, so pulling new code and restarting brings the database up to date: docker compose restart hub.

    The hub runs as the account that owns the checkout, not as www-data, so app/ and core/vendor/ stay yours, as they would on your own LAMP stack. The scheduled tasks are ticked every minute inside the container; the ticks show in docker compose logs hub.

    Commands

    muse runs in the hub's container:

    docker compose exec hub php core/bin/muse migration -f

    docker compose exec runs as root, and muse, as on a server, becomes the account that owns the checkout before it does anything. Other commands do not, so give them your own user number, which id -u prints, with --user. For example, with the number 1000:

    docker compose exec --user 1000 hub core/vendor/bin/phpunit core/libraries/Hubzero/Utility/Tests

    Xdebug

    Xdebug is installed and off. Start the hub with it on, and your editor listening on port 9003:

    XDEBUG_MODE=debug docker compose up -d

    Map /var/www/hub in the container to the checkout in your editor. docker compose up -d without it turns Xdebug off again.

    Changing the ports, or leaving out the sample data

    Compose reads a file named .env beside compose.yaml, if there is one. Set any of these in it before the first start:

    HUB_DEV_PORT=8444
HUB_DEV_MAIL_PORT=8026
HUB_DEV_SAMPLE_DATA=0

    The hub is served on HUB_DEV_PORT both inside its container and out, and the installer writes the address into app/config/app.php. Change the port after the first start and you must change live_site there too.

    Stopping, and starting over

    docker compose stop stops the three containers and docker compose start starts them again. docker compose down removes the containers but keeps the database. To start again from nothing, remove the database volume and the hub's app/ directory as well:

    docker compose down -v
rm -rf app
docker compose up -d

    The setup was run on Ubuntu 24.04 with Docker 29 and Compose 2.40, from a clone with no core/vendor/ and no app/: the first start, restarts, the administrator interface, mail reaching Mailpit, the scheduled tasks, muse through docker compose exec, and Xdebug switched on and off. Nothing it wrote in the checkout belonged to root. It was not tried on macOS or Windows.

    Replacing a hub's CMS with a checkout

    On a hub installed from packages, the CMS directory is a snapshot from when the package was built. To develop against current code, replace it with a clone. The hub's own state lives in app/, which is not in the repository — .gitignore excludes app/** — so app/ is what you carry across.

    Warning: Do this on a development hub only. Take a database dump first; muse migration changes the schema and reversing a migration is difficult.

    1. Change into the web root and move the existing installation aside. The directory is named for the hub name given to hzcms install:

      cd /var/www
sudo mv example example.bak

    2. Clone the repository into its place. The repository is hubzero/hubzero-cms; the older hubzero/hubzero name in the previous version of this page is wrong.

      sudo git clone https://github.com/hubzero/hubzero-cms.git example

    3. Copy the hub's own state back in. This is the configuration, the uploaded files, and the site's templates and extensions.

      sudo cp -a example.bak/app example/

    4. Install the PHP dependencies. core/vendor/ is not in the repository either.

      cd /var/www/example/core
sudo php ./bin/composer install

    5. Bring the database schema up to the code. Run this from the hub root, not from core/:

      cd /var/www/example
sudo php core/bin/muse migration -f

      muse migration with no options is a dry run that lists what it would do; -f performs the run. The -i flag the old page used is deprecated and now behaves as -a (list all), so -f alone is what you want.

    6. Give the web server ownership and let your account write:

      cd /var/www
sudo chown -R apache:apache example
sudo chmod -R 775 example
sudo usermod -aG apache $USER

      The user is apache on Enterprise Linux and www-data on Debian and Ubuntu.

    Warning: Group-writable files owned by the web server user are for a development machine only. Do not carry this permission scheme to a hub anyone else uses.

    Afterwards, git pull --rebase from the hub root brings in new code. Rebase keeps your own unpushed commits on top of it. Re-run steps 4 and 5 when the dependencies or the migrations change.

    Continuous integration

    Three workflows, in .github/workflows/:

    • php-lint.yml — runs on PHP 8.3. Three checks: php -l over every PHP file under core/ and app/ outside vendor/; docs/_tools/lint/missing-facade-imports.php, which fails on any namespaced file that uses a facade without importing it; and docs/_tools/lint/undefined-language-keys.php --quiet --max=444, which fails if the number of language keys nothing defines rises above the current count. The second exists because such a file parses cleanly and misbehaves only when the line runs — see Facades. The third is a ceiling rather than a gate: lower the number as keys are defined.
    • pages.yml — builds this documentation, regenerates the references, checks every internal link, and fails if the committed gh-pages/public/ is stale.
    • dev-push.yml — a deployment hook to a Purdue-operated development host. It is disabled at the top with if: false.

    None of the three runs the PHP test suite, and none starts a browser.

    Running the tests

    PHPUnit is a dev dependency and the tests live beside the code they cover, as *Test.php under core/libraries/Hubzero/ and in each extension's tests/ directory. Run them with core/vendor/bin/phpunit. The database library's tests need their backend available and are run as a separate suite. See Testing.

    For style, core/bin/php_tests.sh <files> gives you the PSR-12 check and the syntax check in one call, the same pair the old Travis configuration ran.
